# CLORA Air-Gap Monitor & Sovereignty — Layered Trust Model

## Problem Statement 26117 (MRPL / SIH)
**Architecture Scope**: Defines the technical boundaries, guarantees, and operational limits of the INDUSAI-X / CLORA Air-Gap Network Monitor.

---

## 1. The Three-Layer Trust Hierarchy

The foundational principle of the CLORA sovereignty architecture is that **Python process monkeypatching is instrumentation, not the OS security boundary**. True air-gap defense rests on layered controls:

```
┌─────────────────────────────────────────────────────────────────────────┐
│ LAYER 1: OS & KERNEL ENFORCEMENT (Primary Boundary)                    │
│ • Host Firewall: Outbound deny rule CLORA_DENY_OUTBOUND                │
│ • Physical/Virtual Network: Disconnected network interface             │
│ • Docker Sandbox: --network none (kernel network namespace isolation)  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
┌────────────────────────────────────▼────────────────────────────────────┐
│ LAYER 2: PROCESS-LEVEL INSTRUMENTATION (This AirGapEnforcer Hook)       │
│ • Hooks socket.socket.connect and socket.getaddrinfo in FastAPI process │
│ • Synchronously intercepts unapproved outbound handshakes              │
│ • Continuous 5-second socket table daemon (BackgroundNetworkAuditor)    │
│ • Startup verification of offline env flags (OLLAMA_NO_CLOUD=1, etc.)  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
┌────────────────────────────────────▼────────────────────────────────────┐
│ LAYER 3: CRYPTOGRAPHIC AUDIT EVIDENCE (Tamper-Evident Proof)           │
│ • SHA-256 Hash Chain (airgap_proof_log.jsonl) linking checkpoints     │
│ • Ed25519 digital signatures (.clora-proof) for workflow reports       │
│ • Verified Offline: Proofs independently checkable without CLORA backend│
└─────────────────────────────────────────────────────────────────────────┘
```

## 2. What This Monitor Sees vs. Does Not See

### Process Scope (`AirGapEnforcer`):
- **SEES**:
  - All `socket.connect()` calls initiated by the FastAPI backend Python process.
  - All `socket.getaddrinfo()` calls initiated by the FastAPI backend Python process.
  - Periodic snapshots of all active TCP/UDP sockets associated with the backend process PID.
- **DOES NOT SEE**:
  - **Ollama daemon binary**: Compiled Go executable running as an independent process outside the Python interpreter. Mitigated via `OLLAMA_NO_CLOUD=1` and host firewall.
  - **Docker sandbox execution**: Child containers managed by dockerd. Mitigated at the Linux kernel level via `--network none`.
  - **Browser / Frontend**: Node.js/Vite development server or client browser traffic. Mitigated via local-only binding (`127.0.0.1:3000`) and npm metrics disabling.

---

## 3. npm & Vite Telemetry Policy

- **Vite**: By design, Vite does not collect or transmit anonymous telemetry during builds or local development. In `frontend/vite.config.js`, `server.host` is explicitly constrained to `127.0.0.1`, preventing exposure to external networks.
- **npm**: npm CLI telemetry is disabled globally by running:
  ```bash
  npm config set send-metrics false --global
  ```
  Verified via `npm config get send-metrics` returning `false`.

---

## 4. Single-Worker SSE Concurrency Constraint

The real-time audit feed (`GET /api/sovereignty/stream`) uses an in-memory `asyncio.Queue` event dispatch pattern.
- **Operational Requirement**: The backend must run under a **single worker** process (`uvicorn --workers 1` or default).
- If deployed across multiple worker processes (`WEB_CONCURRENCY > 1`), process memory is not shared, and subscriber queues on worker B will not receive audit events generated by worker A without external Redis pub/sub.
- **Enforcement**: At startup, `lifespan` verifies worker concurrency and raises a critical warning / disables SSE if multiple workers are detected.

## 5. Host Firewall Provisioning

For live evaluator demonstrations and on-premises deployment, create the named outbound deny rule:

### Windows (PowerShell Administrator):
```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup_firewall_rule.ps1
```

### Linux (root / sudo):
```bash
sudo bash scripts/setup_firewall_rule.sh
```

Pre-demo readiness can be validated at any time using:
```bash
python scripts/check_demo_readiness.py
```
